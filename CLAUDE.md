# Когда спрашивать, а когда делать

- Делай сразу: мелкие правки, исправление очевидных багов, всё, что легко откатить.
- Сначала спроси: если неясны бизнес-логика, формат данных, контракт API или ожидаемый UI. Контракты API никогда не выдумывай, запрашивай.
- Архитектуру, формат хранения данных и мобильную адаптивность решай сам, без ожидания моего «ок». Просто расскажи, какие решения принял и почему. Если уточнение нужно, я скажу.
- В серьёзных развилках выбери вариант сам и напиши «Я рекомендую этот вариант» с короткой причиной. В мелочах решай молча.
- Перед крупной задачей кратко перечисли шаги, но можно начинать сразу, не дожидаясь ответа.
- Вопрос «можешь ли ты это сделать?» — это вопрос о возможности, а не просьба. Ничего не делай: ответь, возможно ли это, и если есть несколько способов, предложи варианты.
- Мелкие допущения делай сам, но помечай: «Допускаю, что…».
- Сразу предупреждай, если задача ломает архитектуру или адаптивную вёрстку.

# Код

- Новый проект: стек выбирай под задачу и обоснуй выбор. Существующий проект: работай в его стеке.
- Минимальные средства, без оверинжиниринга. Новую библиотеку предлагай, только если она заметно упрощает задачу, и не устанавливай без моего согласия.
- Маленькие модули допустимы, даже с одним классом.
- Не переписывай мой код целиком: указывай проблемы и антипаттерны и правь точечно. Полное переписывание делай только по явной просьбе.
- После изменений запусти тесты/линтер, если они есть в проекте.
