## 2. Принятые архитектурные решения

### 2.1. Модель данных **[моё решение]**

```
Category   id, name, name_key (casefold, ё→е; уникальное, см. 2.7)
Tag        id, name, name_key (то же)
Record     id, title, description (кратко, простой текст),
           search_text (название + краткое описание в виде name_key, для поиска),
           text (основной, очищенный HTML), category_id → Category,
           video_url (необязательная ссылка, скрыто, см. 2.4),
           views (счётчик просмотров, см. 3.2),
           is_published (черновик/опубликовано), created_at, updated_at
RecordTag  record_id, tag_id (составной первичный ключ)
RecordRelated      record_id, related_id (связанные записи, см. 3.1)
RecordPrerequisite record_id, requires_id (сначала освой, см. 3.1)
DailyVisits        date, views (просмотры за день, см. 3.2)
Image      id, record_id → Record (удаляется вместе с записью),
           filename, alt, position (порядок), created_at
```

Что изменено относительно текущего кода:
- категория это строка `record_type` → отдельная таблица `Category` (иначе не сделать
  «расширяемый из админки» список);
- убираю поле `author` (админ один, поле нигде не заполнялось);
- добавляю `updated_at` и `is_published` (черновики, см. 5.2);
- в SQLite включаю проверку внешних ключей (`PRAGMA foreign_keys=ON`), режим WAL и
  `AUTOINCREMENT` для `id` записей (номера не переиспользуются, см. 2.7).

Категория у записи ровно одна, тегов сколько угодно.
Предустановленные категории при первом запуске: команда, упражнение, игра, игрушка.
Предустановленные теги: Лёгкий, Средний, Тяжёлый (сложность). Дальше всё создаёт админ.

### 2.2. Формат хранения основного текста **[рекомендую]**

**Храним очищенный HTML** от Quill. Не Delta (внутренний JSON Quill).
- HTML выводится на странице напрямую, без дополнительного рендера;
- ты сам просил «тело записи это html шаблон» (п. 4 ТЗ).

Правило: HTML очищается через `nh3` **на сервере, при сохранении**. В базе лежит уже
чистый текст. Тот же текст идёт в экспорт.

Разрешённые теги: `p, br, h2, h3, strong, em, u, s, ul, ol, li, blockquote, a`.
У `a` разрешены только `href` со схемами `http`, `https`, `mailto`; сервер сам
добавляет `rel="noopener noreferrer"`. **`img` не разрешён**: картинки живут отдельно
(раздел 4), поэтому очистка проще, а риск ниже.

**[риск]** Quill 2 хранит списки как `<ol><li data-list="bullet">`, а не `<ul>`.
Значит, `nh3` должен пропускать атрибут `data-list` у `li`, а в CSS публичной страницы
нужно стилизовать `li[data-list="bullet"]` и `li[data-list="ordered"]`. Проверю на
реальном выводе при реализации.

### 2.3. Quill **[моё решение]**
Файлы кладутся в `static/vendor/quill/` (js и css, версия зафиксирована).
Панель инструментов: заголовки (h2, h3), жирный, курсив, подчёркнутый, зачёркнутый,
списки, цитата, ссылка, очистка форматирования. **Без кнопки картинки и видео.**
Форма отправляет HTML через скрытое поле. Краткое описание это обычный `textarea`
(простой текст), не Quill. Quill остаётся обычным JS и **не** оборачивается в Vue
(сторонние обёртки не нужны, см. 2.8).

### 2.4. Видео (скрыто по умолчанию) **[моё решение]**
Заготовка делается сразу, чтобы потом не менять схему БД и шаблоны:
- в `.env` и в настройках флаг `VIDEO_ENABLED` (по умолчанию `false`);
- колонка `video_url` в записи есть всегда, но при `false` поле не показывается в
  форме админки и видео не выводится на странице записи;
- чтобы включить видео, достаточно поставить `VIDEO_ENABLED=true` (одна строка);
- в записи хранится только ссылка. На странице она превращается во встроенный
  плеер (`<iframe>`) **только для разрешённых сайтов** (YouTube, RuTube, VK Видео;
  список в одном месте в коде). Остальные ссылки отклоняются при сохранении: иначе в
  страницу можно встроить что угодно.
- на телефоне плеер адаптивный (пропорции 16:9, ширина 100%).

### 2.5. Маршруты **[моё решение]**

Публичные:
- `/` список карточек. Фильтры комбинируются через параметры:
  `/?category=3&tag=5&q=лежать&page=2`
- `/record/{id}` страница записи (черновики не показываются).

Админские:
- `/admin` список всех записей (включая черновики) с поиском и кнопками;
- `/admin/new`, `/admin/edit/{id}` форма записи (Quill, картинки, теги, категория);
- `/admin/preview/{id}` предпросмотр (тот же шаблон, что у читателя, виден и черновик, просмотры не считаются);
- JSON-эндпоинты для интерактивных частей формы (контракт описан в 2.8): `/admin/api/...`;
- `POST /admin/delete/{id}` удаление (с подтверждением в браузере);
- `/admin/taxonomy` отдельная страница тегов и категорий (раздел 6);
- `/admin/export` и `/admin/import` (раздел 7).

Служебный: `/health` (проверка, что сайт жив).

Выбираю параметры вместо адресов вида `/category/komanda`, чтобы не заводить slug:
фильтры по категории, тегу и поиск работают вместе без лишних маршрутов.

### 2.6. Миграции схемы **[рекомендую]**
Alembic не подключаю. Схема меняется сейчас (категории в отдельной таблице и т.д.), но
проект маленький, а у нас появляется экспорт и импорт. Порядок при изменении схемы:
экспорт → удалить файл БД → запуск (таблицы создаются заново) → импорт.
Если проект вырастет и данных будет много, вернёмся к Alembic.

### 2.7. Технические исправления первой версии **[моё решение]**

1. **Регистр кириллицы в SQLite.** `LIKE` и `COLLATE NOCASE` игнорируют регистр только у
   ASCII. Поэтому уникальность тегов и категорий проверяется по `name_key`
   (`casefold()` и `ё→е`, считает Python), а поиск идёт `LIKE` по колонке `search_text`
   в таком же виде. Запрос читателя нормализуется так же.
2. **`AUTOINCREMENT`** у `Record.id`: номер удалённой записи не выдаётся повторно, старые
   ссылки `/record/{id}` не начнут вести на чужой контент.
3. **Загрузка картинок по одной** (отдельный запрос на каждый файл). Размер запроса
   ограничен 12 МБ (nginx `client_max_body_size 12m`), а не 100 МБ.
4. **Порядок при сохранении файлов:** сначала commit в БД, потом удаление старых файлов с
   диска. Сбой оставит лишний файл (его найдёт команда проверки), но не битую ссылку.
5. **Импорт чистит HTML через `nh3`** так же, как форма: файл не должен быть обходом
   очистки.
6. **Ссылка «назад к списку»** строится из белого списка параметров (`category`, `tag`,
   `q`, `page`), а не из `Referer`: так нет открытых редиректов.
7. **Синхронные маршруты** (`def`, не `async def`): SQLAlchemy и Pillow синхронные,
   FastAPI сам выполняет их в пуле потоков. Один процесс uvicorn, SQLite в режиме WAL.
8. **Время** хранится в UTC, показывается в часовом поясе из `.env` (`SITE_TIMEZONE`,
   по умолчанию `Europe/Moscow`) **[допускаю]**.
9. **Python 3.14** (текущий) сохраняется: для него есть готовые колёса `Pillow` и `nh3`,
   а Ubuntu 26.04 на VPS поставляется с тем же Python.

### 2.8. Vue: где нужен, а где нет **[рекомендую]**

**Публичный сайт без Vue.** Страницы отдаёт сервер (Jinja). Так быстрее на мобильной сети,
нет JS-каркаса, поисковики видят весь текст сразу. Фильтры, поиск и пагинация это обычные
ссылки.

**Vue только в админке**, и только там, где у блока есть собственное состояние с
несколькими связанными режимами. Всё остальное остаётся обычным HTML и формами, которые
работают и без JS.

| Блок | Решение | Почему |
|---|---|---|
| Менеджер картинок записи | **Vue** | загрузка с прогрессом и ошибками по каждому файлу, порядок, alt, удаление, обложка |
| Выбор «Сначала освой» / «Связанные» | **Vue** | фильтр по названию, список чекбоксов, исключение текущей записи, подсчёт выбранных |
| Выбор тегов с быстрым добавлением | **Vue** | список из БД, поиск, создание нового без перезагрузки формы |
| Форма записи в целом, Quill | обычный JS | Quill не обёртываем в Vue, форма отправляется обычным `POST` |
| `/admin/taxonomy` | обычные формы (`POST` + редирект) | простые действия, работает без JS |
| Автосохранение, предупреждение при уходе, подтверждение удаления | обычный JS | несколько строк |
| Список записей, статистика | Jinja | только вывод |

**Как подключается (без сборки, без Node):**
- файл Vue 3 (глобальная сборка с компилятором, версия зафиксирована) лежит в
  `static/vendor/vue/`, как и Quill; с CDN ничего не грузится;
- компоненты это обычные ES-модули в `static/admin/` (по одному файлу на блок);
- у Jinja и Vue разные скобки: Vue настраивается на `[[ ]]`, шаблоны не конфликтуют;
- начальные данные передаются со страницы через `<script type="application/json">`
  (`|tojson`), а не отдельным запросом;
- блок монтируется в свой `<div>` внутри обычной формы и пишет выбранное в скрытые поля
  (`<input type="hidden" name="related_ids">`), поэтому форма по-прежнему отправляется
  одним обычным `POST`;
- если позже блоков станет много или понадобятся `.vue`-файлы, переходим на Vite. Сейчас
  это оверинжиниринг.

**Контракт JSON-эндпоинтов** (внутренний, между моей админкой и моим сервером; ошибки
всегда `{"detail": "текст по-русски"}`):

| Метод и адрес | Тело и ответ |
|---|---|
| `POST /admin/api/records/{id}/images` | `multipart`, поле `file`. Ответ 201: `{id, url, thumb_url, alt, position}` |
| `PATCH /admin/api/images/{id}` | `{alt}` |
| `PUT /admin/api/records/{id}/images/order` | `{ids: [id, ...]}`, полный новый порядок |
| `DELETE /admin/api/images/{id}` | 204 |
| `POST /admin/api/tags` | `{name}`. Ответ: `{id, name}` (если тег уже есть, отдаётся существующий) |

Список записей для выбора связей и список тегов вшиваются в страницу (`|tojson`), отдельных
эндпоинтов не нужно. Менеджер картинок на странице **новой** записи скрыт с подсказкой
«Сначала сохраните запись, потом добавьте картинки»: после первого сохранения
открывается страница редактирования **[допускаю]**.

- Мета-теги `description` и Open Graph (название, краткое описание, превью-картинка)

- Печатная версия записи (`@media print`: без шапки и меню) **[моё решение, низкий

Не делаю (лишнее на этом этапе): тёмная тема, комментарии, регистрация читателей, slug,

### 3.1. Связанные записи и «Сначала освой» **[моё решение]**

Два разных вида связи между записями, оба ставит админ в форме записи:

**«Связанные записи»**: просто «смотри также». Связь симметричная: если A связана с B,
то B тоже показывает A (в базе пара хранится один раз). На странице записи под основным
текстом выводятся компактные карточки (превью, название), не больше 6.

**«Сначала освой»**: порядок обучения (например, у «Лежать» стоит «Сидеть»). Связь
направленная.
- На странице записи A: блок «Сначала освой» со ссылками на записи, которые нужно
  изучить до неё (в верхней части страницы, после шапки).
- На странице записи B, которая сама входит в чей-то список «Сначала освой», автоматически
  появляется обратный блок «Что изучать дальше» (записи, для которых B является
  предпосылкой). Админу вручную ничего заполнять не нужно.

**Общие правила:**
- если в блоке нечего показывать, блок целиком скрыт (нет заголовка и пустого места);
- запись нельзя связать саму с собой, дубли связей запрещены;
- в «Сначала освой» запрещены **циклы** (A требует B, а B требует A, в том числе через
  цепочку): админка отклонит сохранение понятным сообщением;
- черновики и неопубликованные записи в публичных блоках не показываются;
- при удалении записи все её связи удаляются автоматически (внешние ключи с каскадом);
- в форме записи два блока выбора: поле-фильтр по названию и прокручиваемый список
  чекбоксов (название и категория), текущая запись в списке отсутствует. Работает на
  телефоне, сторонних библиотек не нужно;
- в экспорте связи записываются списками `id`: `related` и `requires` (см. 7.1).

### 3.2. Статистика посещений (самая базовая) **[моё решение]**
- Счётчик просмотров у каждой записи (`views`) и общий счётчик по дням
  (`DailyVisits`). Считаются открытия страницы записи.
- Не считаются: боты (по `User-Agent`: `bot`, `crawler`, `spider`, `curl` и т.п.),
  предпросмотр из админки.
- Cookie, IP-адреса и любые персональные данные **не хранятся**. Уникальных посетителей
  не считаем, поэтому баннер про cookie не нужен.
- В админке: колонка «Просмотры» в списке записей и страница `/admin/stats`: всего,
  за 7 и 30 дней, топ-10 записей, таблица по дням за последние 30 дней (без графиков и
  сторонних библиотек).
- Публично счётчики не показываются.
- В экспорт JSON счётчики не входят (это служебные данные, не контент); в бэкап файла БД
  входят.
- Если когда-нибудь понадобится больше (источники, страны, устройства): утилита
  GoAccess по логам nginx, без изменений в коде.

### 3.3. SEO для открытого сайта **[рекомендую]**
- `sitemap.xml` из опубликованных записей и `robots.txt` (закрыть `/admin` от
  поисковиков);
- `canonical`-ссылка и уникальные `title` и `description` на каждой странице;
- разметка `schema.org/Article` (JSON-LD) на странице записи;
- черновики в карту сайта не попадают.

### 3.4. Обязательные поля и публикация **[твоё решение]**
- Черновик: обязательны только название (до 120 символов) и категория.
- Публикация: дополнительно нужен основной текст (пустой Quill `<p><br></p>` считается
  пустым).
- Краткое описание необязательно (до 300 символов). Если пусто, карточка берёт первые
  ~150 символов основного текста без разметки.
- Выбор категории обязателен всегда, поэтому запись без категории невозможна.

## 4. Изображения **[рекомендую: отдельная галерея записи]**

Картинки не вставляются внутрь текста, а прикрепляются к записи списком.
Первая в списке (`position = 0`) это превью на карточке (п. 5 ТЗ).

**В админке** (блок на Vue, контракт эндпоинтов в 2.8):
- в форме записи блок «Изображения»: выбор нескольких файлов, каждый уходит отдельным
  запросом, с индикатором и ошибкой по каждому файлу;
- у каждой уже загруженной картинки: миниатюра, поле `alt`, кнопки «выше/ниже»,
  «удалить»;
- превью-картинка помечена («обложка»);
- на телефоне тоже удобно (кнопки крупные).

**На сервере:**
- файлы лежат в папке `uploads/` на диске, в БД только имя файла и `alt`;
- имя файла генерируется (`uuid4().hex` + расширение), имя от пользователя игнорируется;
- допустимые типы на входе: jpeg, png, webp. Тип проверяется по **содержимому** файла
  (его открывает Pillow), а не по расширению. Анимированные GIF не принимаю
  (тяжёлые для мобильной сети) **[моё решение]**;
- лимиты: до 10 МБ на загружаемый файл (фото с телефона бывает 5–8 МБ, после
  обработки оно станет в разы легче), до 10 картинок на запись **[моё решение]**;
- обработка Pillow при загрузке (см. ниже);
- удаление записи или картинки удаляет и файл с диска, поэтому «осиротевших» файлов
  не накапливается; на случай сбоя будет команда проверки (файлы без записи в БД и
  записи без файла).

**На публичной странице:**
- `<img loading="lazy">`, `max-width: 100%`, `alt` из БД;
- задаются пропорции (`aspect-ratio`), чтобы страница не «прыгала» при загрузке;
- на телефоне галерея листается горизонтально, на широком экране сетка.

**Pillow: добавляю [рекомендую].** Сайт мобильный, на VPS диск и трафик платные, а
фото с телефона весят 3–8 МБ. Что делает обработка при загрузке:
1. открывает файл и проверяет, что это действительно картинка; ограничивает число
   пикселей (защита от «бомб» вроде огромной картинки в крошечном файле);
2. поворачивает по EXIF (иначе фото с телефона бывают «на боку») и **удаляет все
   метаданные**, включая GPS-координаты, которые телефон пишет в фото. Для открытого
   сайта это вопрос приватности;
3. уменьшает так, чтобы длинная сторона была не больше 1600 px;
4. сохраняет в WebP (качество около 82): он заметно легче JPEG/PNG и поддерживается
   всеми современными браузерами;
5. делает вторую, маленькую копию (480 px по длинной стороне) для карточек на главной.
   Список карточек на телефоне не грузит большие файлы.

В БД хранится одно имя файла (`<uuid>.webp`), миниатюра лежит рядом (`<uuid>_thumb.webp`)
и находится по этому правилу. Оригинал **не** сохраняется (экономим место; если нужно
хранить оригиналы, скажи).

Зависимость: `Pillow` добавится в `requirements.txt` на этапе 4.

## 5. Админка: записи

### 5.1. Список
Поиск, фильтр по категории и статусу (черновик/опубликовано), счётчик, колонка
«Просмотры», кнопки «изменить / удалить». На телефоне кнопки не меньше 44×44 px (сейчас это мелкие эмодзи).

### 5.2. Черновики **[моё решение]**
Флажок «опубликовано». Черновик виден только в админке. Позволяет писать запись в
несколько заходов.
**[риск]** Админка не защищена, поэтому черновики видит любой, кто знает адрес
`/admin`. Для секретных заметок черновики не подходят.

### 5.3. Форма записи
- Поля: название, категория (выпадающий список из БД), краткое описание, основной
  текст (Quill), теги (чекбоксы из БД + быстрое добавление нового тега), изображения,
  «Сначала освой» и «Связанные записи» (выбор из существующих, см. 3.1), флажок
  «опубликовано».
- Ошибки валидации показываются в форме рядом с полем, а не сырым JSON.
- После сохранения сообщение «Запись сохранена».
- Кнопка «Предпросмотр» (в новой вкладке, в том же виде, как увидит читатель).
- Автосохранение черновика формы в браузере (localStorage), чтобы длинный текст не
  терялся при закрытии вкладки.
- Предупреждение при уходе со страницы с несохранёнными изменениями.
- Кнопка «Дублировать запись» **[моё решение]**.

### 5.4. Удаление
Корзины нет. Удаление записи необратимо (вместе с её картинками), поэтому перед ним
всегда подтверждение. Страховка от ошибок это бэкап (раздел 7.4).

## 6. Админка: теги и категории (отдельная страница)

`/admin/taxonomy`, два блока: «Категории» и «Теги».

**Общие правила** **[моё решение]**:
- название без лишних пробелов, не пустое, до 40 символов;
- уникальность без учёта регистра («Легкий» и «легкий» одно и то же);
- рядом с каждым пунктом счётчик «используется в N записях».

**Теги**: добавить, переименовать, удалить. Удаление тега просто снимает его со всех
записей (счётчик показывается заранее). Для дублей: «объединить с…» (все записи
перейдут на выбранный тег).

**Категории**: добавить, переименовать, удалить. Удалить категорию, к которой привязаны
записи, **нельзя**: админка покажет «используется в N записях» и предложит сначала
перенести их в другую категорию **[рекомендую]**: так запись никогда не остаётся без
категории.

Порядок категорий в навигации: по порядку создания.

## 7. Экспорт и импорт JSON

Цель: бэкап и передача данных языковой модели.

### 7.1. Состав данных **[моё решение]**
Поля, которые назвал ты: `id`, `title` (название), `description` (краткий текст),
`text` (основной текст), `tags`. Дополнительно (твой ответ): `is_published` и `created_at`,
иначе после «экспорт → импорт» все черновики стали бы опубликованными, а даты потерялись. Добавляю `category` (название категории): это тоже
текст, и без него при импорте категория потеряется.
Картинки в JSON **не входят** (бинарные файлы; для них нужна копия папки `uploads/`).
Поле `video_url` (когда видео включено) входит в экспорт как обычное текстовое поле.
Связи записей входят как списки `id`: `related` (связанные записи) и `requires`
(«сначала освой»). Счётчики просмотров не входят (3.2).

Пример:

```json
{
  "schema_version": 1,
  "exported_at": "2026-10-20T12:00:00+00:00",
  "records": [
    {
      "id": 1,
      "title": "Команда «Сидеть»",
      "category": "команда",
      "is_published": true,
      "created_at": "2026-10-01T09:30:00+00:00",
      "description": "Базовая команда для щенка.",
      "text": "<p>Возьмите лакомство…</p>",
      "tags": ["Лёгкий уровень", "Послушание"],
      "related": [4, 7],
      "requires": []
    }
  ]
}
```

### 7.2. Будущие текстовые поля **[рекомендую]**
Список экспортируемых полей задаётся **в одном месте в коде** (одна схема pydantic
`RecordExport`). Добавить новое текстовое поле это: колонка в модели, поле в форме,
строка в этой схеме. Экспорт и импорт подхватят его сами. Импорт устойчив к
несовпадению версий: незнакомые поля в файле игнорируются (с предупреждением), а
недостающие берут значения по умолчанию.
Связи (`related`, `requires`) импорт восстанавливает вторым проходом, после
создания всех записей. Если `id` из списка в файле не найден, связь пропускается с
предупреждением в отчёте.

### 7.3. Формат выгрузки **[твоё решение]**
Один формат, без отдельных режимов. Файл предназначен и для бэкапа, и для передачи
языковой модели: в него попадает ровно то, что лежит в базе (основной текст остаётся
очищенным HTML). Специальной конвертации «в чистый текст» нет: модель сама читает этот
текст. Он же без изменений загружается обратно импортом.

Файл читается человеком: отступы и `ensure_ascii=False`, чтобы русский текст был
читаемым, а не набором экранированных кодов.

### 7.4. Импорт и безопасность данных **[рекомендую]**
Админка открыта всем, а корзины нет, поэтому правила строгие:
- импорт из браузера работает только в режиме **«добавить и обновить»** (запись с
  существующим `id` обновляется, с новым добавляется; незнакомые теги и категории
  создаются);
- режим **«заменить всё»** доступен **только из терминала** (команда запускается на
  сервере), через сайт его нет. Иначе любой посетитель одним запросом сотрёт базу;
- перед каждым импортом файл БД **автоматически копируется** в папку `backups/`
  (хранятся последние 10 копий);
- импорт проходит проверку формата (pydantic). При ошибке в любой записи не
  сохраняется ничего, пользователь видит, где ошибка;
- в конце отчёт: «добавлено N, обновлено M, пропущено K».

Команды в терминале: `python -m cli export`, `python -m cli import файл.json
[--replace]`, `python -m cli backup` **[моё решение]**.

### 7.5. Ежедневный бэкап на VPS **[рекомендую]**
- Скрипт `scripts/backup.sh` (в репозитории) раз в сутки по cron: безопасно копирует
  файл SQLite (через `sqlite3 .backup`, а не простым `cp`, чтобы копия не оказалась
  «битой» во время записи), складывает в `backups/` вместе с архивом `uploads/`,
  хранит последние 14 дней.
- **Копия на том же диске не спасает от потери самого диска.** Внешняя копия будет на
  **Google Диске** **[твоё решение]**. **TODO: добавить.** Пока в `scripts/backup.sh`
  стоит заглушка: отдельная функция `upload_to_gdrive()`, которая только пишет в лог
  «внешняя копия не настроена». Когда дойдём, подключим её (вероятно, через `rclone`,
  это отдельная программа на VPS, не библиотека Python).
- Подробную инструкцию (как поставить cron на VPS) напишу в README на этапе 7.

## 8. Адаптивность (п. 9 ТЗ)

### 8.1. Принципы **[моё решение]**
- Вёрстка «сначала мобильная»: базовые стили для телефона, шире это дополнения.
- Контрольные ширины для проверки: 360, 390, 768, 1024, 1440 px. На всех: **нет
  горизонтальной прокрутки**.
- Сетка карточек: 1 колонка до 640 px, 2 колонки от 640 px, 3 от 1024 px.
- Области нажатия не меньше 44×44 px (кнопки, чипы, теги-ссылки, чекбоксы).
- Размер шрифта основного текста не меньше 16 px (иначе iOS приближает страницу при
  фокусе в поле).
- Админка адаптивна так же: форма в одну колонку, Quill-панель переносится, список
  записей превращается в карточки.

### 8.2. Картинки на мобильных
`max-width: 100%`, ленивая загрузка, фиксированные пропорции, горизонтальная
прокрутка галереи с привязкой (scroll-snap).

### 8.3. Краткое описание без наведения **[рекомендую]**
Сейчас описание «всплывает при наведении» на карточку. На телефоне наведения нет,
значит, краткое описание там не увидеть. Решение: на устройствах без наведения
(`@media (hover: none)`) краткое описание **постоянно** показывается под названием,
сжатое до 2–3 строк. На десктопе остаётся текущее поведение.

### 8.4. Скорость
Шрифты Google Fonts подключены сторонним запросом. Пока оставляю; позже можно
хранить локально, если важна скорость или приватность.

## 9. Безопасность и риски

Админка в коде не защищена, защита стоит перед ней в nginx (пункт 3). Если nginx
настроен неверно, действует всё сказанное ниже:

1. **Любой в интернете может** создавать, править и удалять записи, добавлять и
   удалять теги и категории, загружать файлы на сервер и запускать импорт.
   **Страховка:** автоматический бэкап перед импортом (7.4), ежедневная копия БД и
   `uploads/` (рекомендую настроить на сервере), «заменить всё» только из терминала.
2. **Загрузка файлов открыта всем.** Меры в коде: проверка по содержимому, лимиты на
   размер и количество, сгенерированные имена, `uploads/` отдаётся как статика без
   выполнения. Ещё один слой (лимит размера запроса) настраивается на веб-сервере
   (например `client_max_body_size` в nginx) при выкладке.
3. **Защита админки [твоё решение]:** Basic Auth на уровне nginx для `/admin*`
   (`auth_basic`, файл паролей на сервере, создаётся командой `htpasswd`). В коде
   приложения авторизации нет, на локальной машине админка открыта. Пароль защищает и
   JSON-эндпоинты `/admin/api/*`. Это закрывает пункт 1 для посторонних, остальные меры
   остаются как вторая линия. Basic Auth работает только по HTTPS (раздел 12).
4. **XSS** закрыт очисткой HTML через `nh3` и запретом `img` в тексте. Название, краткое
   описание, теги и `alt` выводятся Jinja с автоматическим экранированием.
5. **CSRF** при открытой админке не имеет смысла, не делаю.
6. Секреты остаются в `.env` (вне git).

## 10. Тесты **[моё решение]**
Пишу вместе с функциональностью, в первую очередь:
- очистка HTML (скрипты, обработчики событий, `javascript:` в ссылках, `img`);
- загрузка файлов (неверный тип, подмена расширения, слишком большой файл);

  и «легкий» считаются дублем (кириллица, 2.7);
- удаление категории с записями отклоняется;
- связи: запись нельзя связать с собой, цикл в «Сначала освой» отклоняется, пустой
  блок не выводится, связь симметрична, при удалении записи связи исчезают;
- счётчик просмотров: растёт от обычного запроса, не растёт от бота и предпросмотра.

## 11. План реализации **[моё решение]**

Каждый этап заканчивается работающим сайтом и зелёными тестами. Мобильная вёрстка
делается с самого начала (базовые стили для телефона), а не только на этапе доводки.

**Этап 0. Подготовка.** Настройки из `.env` (`DATABASE` от `BASE_DIR`, `SITE_URL`,

тестовой БД, `requirements.txt` (+ `nh3`, `Pillow`). Команды очистки git (pycache из
индекса, `records.db`) подготовлю, коммитить не буду.

### Прототип (после него можно вводить реальные данные)

  `name_key`, `search_text`. Внешние ключи, WAL, `AUTOINCREMENT`. Предустановленные

## 12. Выкладка на VPS **[рекомендую]**

Сайт открыт в интернете, поэтому выкладка входит в проект, а не делается «как получится».
- **Запуск:** uvicorn как служба `systemd` (поднимается после перезагрузки сервера и
  после падения), без `reload`; адрес и порт берутся из `.env`.
- **nginx** перед приложением: сам отдаёт `static/` и `uploads/` (с кэшированием),
  сжимает ответы (gzip), ограничивает размер запроса и частоту POST (`limit_req`, это
  вторая линия защиты от спама), **Basic Auth на `/admin*`** (9, п. 3), закрывает прямой
  доступ к файлу БД и `.env`.
- **HTTPS:** бесплатный сертификат Let's Encrypt (`certbot`), автообновление. Нужен домен
  (его пока нет); без HTTPS Basic Auth передаёт пароль открытым текстом, поэтому админку
  без домена и сертификата в интернет не выставляем.
- **`/health`**: маршрут для проверки, что сайт жив (можно подключить внешний монитор).
- **Логи** в файл с ротацией (logrotate), чтобы диск не заполнился.
- **Бэкап:** скрипт и cron из 7.5.
- **Обновление сайта:** `git pull`, установка зависимостей, перезапуск службы.
- Всё это записывается в README пошагово (команды для Ubuntu/Debian); заранее
  готовлю шаблоны конфигов (`deploy/` в репозитории).
